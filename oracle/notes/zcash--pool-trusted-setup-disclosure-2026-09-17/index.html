METHODOLOGY.md 4.1's own framing for POOL targets (shielded value pools): "No key. Replaced by setup risk: no SRS (Halo 2) scores higher than an MPC SRS (Groth16)." No formula existed for this framing -- this file is the resolution: the facts, cross-checked against the primary source, and an explicit, reasoned decision NOT to turn them into a 0-100 score, rather than leaving the question silently open.

The facts (re-verified against ZIP 224 directly, not just cited from#

ZIP 224's own stated security model for the Groth16 ceremonies: "as long as at least one participant was honest and not compromised, the hidden structure is unrecoverable." If the hidden structure (the "toxic waste") were recovered by a colluding or compromised participant, it "could be used to create fake proofs and thus counterfeit funds" in that specific pool.

Why this is NOT turned into a numeric score, unlike every other target#

in this project

Every other score in this project (all 8 ecosystems, all target types scored so far) is derived from a LIVE, RE-CHECKABLE READ: an eth_call, a getAccountInfo, a GetLightdInfo, a NEAR view_access_key_list -- something a reader can re-run today and get the same answer, or an answer that has genuinely changed. The Groth16 ceremonies' security assumption is categorically different: "was at least one of the 6 Sprout participants (or roughly 90 per round of Sapling's) honest and did they actually destroy their share of the toxic waste" is not something any on-chain read, any API call, or any external verification can answer, today or ever. It is an assumption about historical human conduct during a ceremony that already happened, unfalsifiable by construction (a successful attack using recovered toxic waste would look like ordinary counterfeit spends, and the absence of an attack so far is not proof none occurred, only that a sufficiently sophisticated one hasn't been detected or attempted).

Assigning a 0-100 number here -- even a well-reasoned one -- would present a judgment call about unfalsifiable historical trust with the exact same apparent precision and re-checkability as this project's live RPC-derived scores, which would be misleading about what kind of claim it actually is. This is the same discipline already applied elsewhere in this project to similarly unquantifiable-but-real risks: Uniswap's governance-capture facts (chains/ethereum-l1/scorers.py's score_uniswap_v3_factory() docstring) and the LayerZero DVN configuration nuance on the Ethereum L1 OFTAdapters were both disclosed as facts in notes, not folded into a score, for the same underlying reason -- no defensible calibration basis exists, and a plausible-looking fabricated number is worse than an honest gap.

What CAN be said with confidence, and why it still doesn't produce a number#

  • Orchard and Ironwood have zero such risk, by design, not by probabilistic trust in any ceremony -- Halo 2 needs no SRS at all. This is a categorically different (and strictly stronger) guarantee than "probably at least one of ~90 people was honest."
  • More MPC participants is, if anything, evidence FOR safety, not against it (the opposite polarity from every other multisig-style dimension this project scores elsewhere: a 1-of-90 threshold is normally this project's WORST case, but here "1-of-90 honest suffices" is the SAFEST possible framing of that ceremony). Sapling's ~90-participant ceremony is on this logic more robust than Sprout's 6-participant one -- but "more participants therefore score higher" would still be presenting a plausibility argument as if it were a measured fact, which it is not.
  • A number that TRIED to reflect "Orchard/Ironwood = 100, Sprout/Sapling = some lower number scaled by participant count" would be internally consistent-looking but would rest entirely on an unmeasurable input (true participant honesty), not a live one -- exactly the fabricated-but- plausible number this project's own discipline exists to prevent.

Recommendation for a future pass, not done here#

If this project ever wants a POOL-type score, the honest path is a BINARY/categorical flag (hasTrustedSetup: true/false) published alongside the existing five dimensions as a sixth, clearly-labeled fact -- not folded into adminKeyScore or any existing dimension, and not expressed as a continuous 0-100 number that implies a precision the underlying question does not have. That is a real design decision (a new field, a contract change) outside the scope of what this pass should decide unilaterally.

Open item not resolved by this file#

Shielded pool VALUE (how much ZEC currently sits in Sprout vs. Sapling vs. Orchard, which determines how much is actually at stake if either ceremony were ever compromised) was not read this pass -- METHODOLOGY.md section 2 already notes "shielded state is not readable without viewing keys" via the lightwalletd interface this project's scripts use; a node-level getblockchaininfo-style valuePools read (a different RPC surface, tracked in consensus per ZIP 209 even though individual shielded transactions stay private) was not attempted this pass.
