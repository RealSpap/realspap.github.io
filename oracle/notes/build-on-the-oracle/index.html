Build on the oracle

Three recipes to build on the Authority Risk Oracle, all replayable and all on test networks: read a score on-chain, check the signed files of the Watch without trusting me, and put a guard in front of an action. A score is a reading, not a verdict.

3 recipesreplayable, read-only, on test networks

read at 21:08Z on 23 November 2026. This page needs no script and no tool to read.

I wrote this page from a reading of the oracle on Ethereum Sepolia testnet (chain ID 11155111), the source of its contract and the signed manifest of the Watch, all read on 2026-11-23 at 21:08Z.

Before you start

Everything here is replayable with cast (Foundry) or with curl and Node. The oracle is a contract with a few public functions; a reader only needs the read-only ones. I read the oracle on Ethereum Sepolia testnet (chain ID 11155111) at block 12198184. I asked 3 public nodes; 2 answered at that block and gave the same answers (ethereum-sepolia-rpc.publicnode.com, sepolia.gateway.tenderly.co); 1rpc.io gave no answer at that block. I read the source of the contract at commit fbea6be of the repository.

Recipe 1: read a score on-chain

The oracle 0xB6F8474ccC71AF477c31c2DF663B3942ddfbf906 on Ethereum Sepolia testnet (chain ID 11155111) publishes a score for contracts that live on another network. Here the target 0x1f98431c8ad98523631ae4a59f267346ea31f984 is a contract on Ethereum mainnet (chain ID 1): the score is written on the test network and describes the mainnet contract. Nothing in this recipe writes to a chain and nothing needs a key.

The eight values come back in the order of the comment under the first command: five sub-scores, the composite, the time of the last push, and the hash of the method that computed them. The composite of this contract read 85 at block 12198184. A composite is a number written by a script from public data, with the method named by the hash. It says how strong an authority setup looks; it does not say what will happen.

isStale answered false. The contract says: true if the address was never scored or if the last push is older than maxStaleness. At this block maxStaleness read 777600 seconds (9.0 days), and its admin can change it. lastUpdated is written by the account that pushes the score, not set by the chain, so it is the pusher's claim about the time; the Watch checks it and the page of the Watch is where to look for a push that came late.

A stale example, read at the same block: the contract 0x2cc440b721d2cafd6d64908d6d8c4acc57f8afc3 on Ethereum mainnet (chain ID 1) has isStale true, because its last push is older than maxStaleness. Its values are still stored and still readable; a consumer that skips the isStale call would use them as if they were fresh.

An address that was never scored reads eight zeros, and isStale reads true. The zeros are not a score: they are the answer of a mapping with no entry. This is why the order is always isStale first, then getScore. The address 0x000000000000000000000000000000000000dEaD on Ethereum mainnet (chain ID 1) was never scored. The last block of this recipe shows what block 12198184 answered for it.

The commands of this recipe use --block 12198184, which needs a node that keeps old state: a public node may drop that state after some weeks. The same commands without --block read the latest state.

Recipe 2: read the signed files without trusting me

The Watch reads the oracles and the targets every six hours and publishes files on the branch watch-data. It also publishes a manifest: the sha256 of every file and the head of the hash chain of its journal, signed with an Ed25519 key. You do not have to trust my page, my word or the host of the files: you can check the signature and the hashes yourself.

The first block downloads the signed manifest and prints the sha256 of the scores file of this oracle as you received it. The script below it checks one thing: that the manifest was signed by the pinned key, 11baca3ef6a69de4901c185f6cbbd3f93318fbb74f9961a8d39aead841adf409. The script builds the key from that constant, not from the key written in the file, and prints KEY DIFFERS if the file names another key. The last block prints the sha256 that the manifest records for that same file. When the two sha256 are equal, the file is the one the Watch signed. If they differ, run both again: the Watch may have published a new run between the two downloads. I ran it on 2026-11-23 at 21:08Z: the signature verified and the two hashes were equal.

What this proves: the files are the ones the Watch signed. What it does not prove: that the Watch read the chain correctly, or that its workflow is honest. The workflow holds the signing key; a bad change to it could sign anything, and the repository history would show it. To check a score against the chain, use recipe 1.

Verify the signature with Node (no install; the key is pinned in the script; save as verify.js and run node verify.js)

const fs = require('fs'), c = require('crypto');
const s = JSON.parse(fs.readFileSync('signature.json', 'utf8'));
const canon = function f(o) { return Array.isArray(o) ? '[' + o.map(f).join(',') + ']' : (o && typeof o === 'object') ? '{' + Object.keys(o).sort().map(function (k) { return JSON.stringify(k) + ':' + f(o[k]); }).join(',') + '}' : JSON.stringify(o); };
const msg = canon(s.manifest).replace(/[\u0080-\uffff]/g, function (ch) { return '\\u' + ch.charCodeAt(0).toString(16).padStart(4, '0'); });
const key = c.createPublicKey({ key: Buffer.concat([Buffer.from('302a300506032b6570032100', 'hex'), Buffer.from('11baca3ef6a69de4901c185f6cbbd3f93318fbb74f9961a8d39aead841adf409', 'hex')]), format: 'der', type: 'spki' });
console.log(s.public_key === '11baca3ef6a69de4901c185f6cbbd3f93318fbb74f9961a8d39aead841adf409' ? 'pinned key' : 'KEY DIFFERS', c.verify(null, Buffer.from(msg), key, Buffer.from(s.signature, 'hex')) ? 'signature OK' : 'signature FAILS');

Recipe 3: put a guard in front of an action

The guard is a rule about when to act, not a contract. It acts only if the target's score was read, is fresh, and is above a line that you choose; otherwise it refuses or asks for a confirmation. The line is yours: I do not give one, and no number here is a recommendation.

Each line answers a failure that is easy to miss. A failed read returns nothing, and nothing is not zero. A target that was never scored reads zeros with isStale true, so the stale test comes before the score. Read at the block of your decision, on two nodes that must agree, so that a single node cannot decide for you.

The composite is an aggregate of three of the five sub-scores (admin key, multisig and timelock); the oracle authority and cross exposure scores are not in it, so a guard on the composite alone ignores them: read them too if they matter to you. The admin can raise maxStaleness, so a reader who needs a bound on age can also set its own on lastUpdated. The pusher writes lastUpdated, so a date in the future would keep isStale false: the guard asks in that case.

A score is a reading, not a verdict. A reading above your line allows an action; it does not make the action wise, and a reading below it does not prove a problem.

A guard in a dozen lines (pseudo-code, not a contract to deploy)

def may_act(target, minimum):                    # minimum is a line YOU choose
    stale = oracle_is_stale(target)              # asked first, at one block, two nodes that must agree
    if stale is None:                            # a failed read is not an answer of fresh
        return ask("no staleness reading")
    if stale:                                    # never scored, or older than maxStaleness
        return ask("stale or never scored")
    reading = read_score(target)                 # same block, same two nodes
    if reading is None:                          # a failed read is not a zero
        return ask("no reading")
    if is_after(reading.last_updated, block_time()):    # a date in the future is not fresh either
        return ask("last update in the future")
    if below(reading.composite, minimum):        # below your line
        return refuse("below the line you chose")
    return allow()                               # a reading allowed it, nothing more

What this is not

It is not an audit and not a security rating. It does not say that a contract is sound or that it is not.

It is not investment advice. Nothing here tells you to buy, sell, lend or hold anything.

It is testnet. The oracles publish on test networks, and the contracts they score are on other networks; an address on a testnet has no value. Nothing on this page writes to any chain.

A value without a reading is never zero. A failed call, a missing file or a target that was never scored is a stated absence, and the guard above refuses it or asks.

What I left out

This page covers the oracle on Ethereum Sepolia testnet (chain ID 11155111). The other EVM oracles have the same contract at their own addresses (listed above) and I read only this one; the program on Solana devnet is a different program with its own accounts, described in the repository.

I confirmed that the deployed code answers each read function above and carries the selector of every function in the two tables. Comparing the deployed bytecode with a build of the source is outside what this page does; the repository documents how its own script compares the chain with the Watch.

I took one fresh target, one address that was never scored and, when the file listed one, one stale target, so at most three of the targets of this oracle. The Watch lists all of them.

I did not run a guard against a deployed consumer: the guard is a shape, not a program, and the repository holds an example consumer that reads the composite only.
